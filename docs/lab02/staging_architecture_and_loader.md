# Лабораторна робота 2: Архітектура шарів даних (stg, core, audit) та надійне завантаження у Staging

## 1. Архітектурний поділ: простори імен `stg`, `core` та `audit`

У сучасній інженерії даних підхід розділення сховища на логічні простори імен (PostgreSQL Schemas) є фундаментальним стандартом (патерн **ELT — Extract, Load, Transform** або **Medallion Architecture**):

```
 Джерела (CSV)
      │
      ▼
┌──────────────┐      ┌─────────────────────────┐
│  stg (Raw)   │ ───► │       core (DWH)        │
│ (Bronze / EL)│      │  (Silver / Transformed) │
└──────────────┘      └─────────────────────────┘
      │
      ▼
┌──────────────┐
│ audit (Meta) │
│ (Governance) │
└──────────────┘
```

### Призначення кожного простору імен:

1. **`stg` (Staging / Landing / Bronze Layer):**
   - **Мета:** Максимально швидкий і безпечний прийом сирих даних із первинних джерел без будь-яких видозмін та втрат.
   - **Типи полів:** Усі бізнес-поля зберігаються як `TEXT`. Це критично важливо, оскільки спроба зчитати брудні значення (наприклад, некоректні дати, текстові описки у числових полях) у типізовані колонки призводить до збою завантаження або мовчазної втрати рядків.
   - **Цілісність:** Жодних обмежень `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE` чи `NOT NULL` на бізнес-поля. Навіть дублікати або записи з відсутніми ключами мають бути зафіксовані для подальшого аналізу якості даних.
   - **Метадані:** Кожен запис супроводжується технічними полями (`batch_id`, `source_file`, `source_row_number`, `loaded_at`), що гарантує 100% лінію походження даних (data lineage).

2. **`core` (Core Business Model / Silver / Gold Layer):**
   - **Мета:** Зберігання узгодженої, очищеної, дедуплікованої та валідованої моделі предметної області.
   - **Типи полів:** Строга типізація (`VARCHAR`, `NUMERIC`, `TIMESTAMPTZ`, `BOOLEAN`).
   - **Цілісність:** Жорсткі обмеження цілісності (`PRIMARY KEY`, `FOREIGN KEY`, `CHECK`). Некоректні дані не допускаються або очищуються під час трансформації `stg -> core`.
   - **Мінімальний набір:** Містить лише підтверджені бізнес-поля, необхідні для моделювання сутностей.

3. **`audit` (Audit / Operational Metadata Layer):**
   - **Мета:** Повний моніторинг конвеєрів завантаження, контроль якості та відтворюваності (reproducibility).
   - **Сутності:** Таблиця пакетів (`audit.load_batches`) і файлів (`audit.load_files`), де фіксується статус (`RUNNING`, `SUCCESS`, `FAILED`), кількість прочитаних та записаних рядків, час старту/завершення та повідомлення про помилки.

### Еквівалентні архітектурні моделі в індустрії:
- **Medallion Architecture (Databricks / Delta Lake):** `stg` відповідає **Bronze** (сирі дані з метаданими), `core` відповідає **Silver** (очищені реляційні таблиці), аналітичні агрегати — **Gold**.
- **Inmon Enterprise Data Warehouse:** Landing/Staging Area -> Normalized EDW (3NF Core) -> Data Marts.

## 2. Специфікація мінімальних полів у `core` та збереження полів у `staging`

Згідно з вимогами, вихідні колонки розділені між шарами:

| Таблиця | Мінімальні поля у `core` | Решта полів, що зберігаються у `stg` |
|---|---|---|
| **customers** | `customer_id`, `full_name`, `city`, `registered_at` | `email`, `phone`, `service_zone_id`, `customer_status` |
| **merchants** | `merchant_id`, `merchant_name`, `city`, `opened_at` | `merchant_type`, `service_zone_id`, `merchant_status` |
| **products** | `product_id`, `merchant_id`, `product_name`, `unit_price_uah`, `is_active` | `category`, `updated_at` |
| **orders** | `order_id`, `customer_id`, `merchant_id`, `created_at`, `order_status`, `currency`, `subtotal_amount`, `delivery_fee`, `discount_amount`, `total_amount` | *(усі поля orders входять до core, у stg зберігаються як text)* |
| **order_items** | `order_item_id`, `order_id`, `product_id`, `quantity`, `unit_price`, `line_discount`, `line_total`, `currency` | *(усі поля order_items входять до core, у stg зберігаються як text)* |

### Чому `email` НЕ оголошується унікальним (UNIQUE)?
1. **Відсутність підтвердженого бізнес-правила:** У вимогах чітко зазначено: *"Email не оголошувати унікальним без підтвердженого правила"*.
2. **Фактичні проблеми в даних (Data Profiling Findings):**
   - Як виявлено під час профілювання лабораторної 1 (`docs/data_dictionary.md`), у вибірці `customers.csv` клієнти `S06-C000270`, `S06-C000703`, `S06-C000360` та клієнт у рядку 800 мають однакову пошту.
   - У реальному житті це часті випадки: члени однієї родини використовують спільну пошту, або користувач зареєстрував новий акаунт на ту саму адресу. Оголошення поля `email UNIQUE` призвело б до падіння транзакції завантаження або відкидання валідних клієнтів.

## 3. Вимоги та реалізація завантажувача у Staging (Requirement 3)

Завантажувач реалізовано у модулі [`src/lab02/load_staging.py`](file:///c:/Users/Rabil/Desktop/%D1%83%D0%BD%D1%96%D0%BA/3%D0%BA/%D0%9C%D0%B5%D1%82%D0%BE%D0%B4%D0%B8%20%D1%82%D0%B0%20%D1%82%D0%B5%D1%85%D0%BD%D0%BE%D0%BB%D0%BE%D0%B3%D1%96%D1%97%20%D1%96%D0%BD%D0%B6%D0%B5%D0%BD%D0%B5%D1%80%D1%96%D1%97%20%D0%B4%D0%B0%D0%BD%D0%B8%D1%85/src/lab02/load_staging.py).

### Реалізація ключових правил:

1. **Явна перевірка заголовка та порядку колонок:**
   - Перед читанням даних функція `validate_csv_header()` порівнює фактичний список колонок із файлу із суворо очікуваним списком.
   - Якщо назва хоча б однієї колонки відрізняється, пропущена або порядок змінений — негайно викидається `StructuralValidationError` і завантаження файлу блокується.
2. **Структурно зламаний файл зупиняє пакет (жодного мовчазного пропуску `bad lines`):**
   - Замість `on_bad_lines='skip'`, кожен рядок перевіряється на відповідність кількості колонок (`len(row) == expected_col_count`).
   - Якщо рядок містить забагато або замало роздільників — пакет негайно зупиняється, транзакція відкочується (`ROLLBACK`), а в `audit.load_batches` фіксується статус `FAILED`.
3. **Кількість у staging збігається з кількістю записів у CSV:**
   - Усі рядки (включно з дублікатами) записуються до `stg`.
   - Після запису виконується контрольний запит `SELECT COUNT(*) FROM stg.<table> WHERE batch_id = %s`, який звіряється з кількістю рядків у файлі.
4. **Дані передаються параметрами, а не конкатенацією SQL:**
   - Запити формуються виключно через плейсхолдери `%s` з передачею списку кортежів через `psycopg2.extras.execute_values`. Це унеможливлює SQL-ін'єкції та синтаксичні помилки при наявності лапок чи спецсимволів у тексті.
5. **Технічні поля метаданих:**
   - `batch_id`: унікальний ідентифікатор сесії імпорту (`batch_YYYYMMDD_HHMMSS_<hex>`).
   - `source_file`: ім'я вихідного файлу (`customers.csv` тощо).
   - `source_row_number`: номер запису в CSV після заголовка (починається з 1, строго фіксує фізичне місце рядка у файлі).
   - `loaded_at`: точний час завантаження з таймзоною (`clock_timestamp()`).

